建立一個專屬資工系學生與新鮮人的專業辭典，能精準解決「上課聽不懂專有名詞」與「實務情境對不上」的痛點。

這份 MVP（最小可行性產品）專案規劃以快速上線、功能精準、技術單純為核心，讓你能在最短時間內產出可用的原型。

MVP 系統架構與技術選型
平台層級	建議技術 Stack	選用理由
前端 (Frontend)	React / Next.js + Tailwind CSS	開發速度快、UI 元件庫豐富、對 SEO 與搜尋體驗友善
後端 (Backend)	Node.js (Express) 或 Python (FastAPI)	FastAPI 處理模糊搜尋演演算法（如 Levenshtein Distance）與文字處理非常方便
資料庫 (Database)	PostgreSQL + pgvector 或 MongoDB	支援全內文檢索與向量/模糊比對，方便未來擴充 AI 語義搜尋
部署 (Deployment)	Vercel (前端) + Render / Railway (後端)	免費額度足夠 MVP 階段測試與展示
資料結構設計 (Data Schema)
單字資料表是整個系統的核心，需包含分類與使用情境：

JSON
{
  "id": "term_001",
  "word_en": "RAG",
  "word_zh": "檢索增強生成",
  "full_name": "Retrieval-Augmented Generation",
  "definition": "結合檢索系統與大語言模型的技術，讓 AI 能參考外部知識庫來回答問題。",
  "category": ["人工智慧", "自然語言處理"],
  "application_scenarios": [
    "企業內部知識庫",
    "文件問答",
    "客服機器人",
    "技術文件助手",
    "AI 搜尋引擎"
  ],
  "example_sentence": "這家公司想做內部資料庫問答，建議使用 RAG 架構來降低 AI 幻覺。"
}
關鍵功能實作規劃
1. 拼字容錯與相關單字推薦 (Fuzzy Search / Auto-Correction)
當使用者輸入拼錯的英文時（例如輸入 RAGg 或 Recursion 拼錯），需在搜尋欄下方提示「你是不是要找...？」。

前端邏輯：搜尋欄輸入時觸發 Debounce（防抖機制，約 300ms），避免頻繁發送 API。

後端邏輯：

使用 Levenshtein Distance（編輯距離演算法） 或 PostgreSQL 的 pg_trgm（三元組模糊比對）。

計算輸入字串與資料庫中 word_en 的相似度，取前 3～5 個最接近的單字回傳給前端作為 Dropdown 建議。

2. 標籤與使用情境導覽 (Scenarios & Categories)
情境關鍵字搜尋：搜尋欄不僅比對英文單字，同時比對 application_scenarios（例如搜尋「客服機器人」時，也會出現 RAG）。

分類篩選區：按「作業系統」、「網路」、「人工智慧」、「軟體工程」等大分類篩選。

MVP 開發時程與任務拆解 (4 週計畫)
1
週一：資料庫與 API 規範設計
奠定資料基礎
確定 JSON / 資料庫 Schema 設計。

先手動整理 50–100 個資工常聽到的名詞（如 RAG, Deadlock, Polymorphism, CI/CD, Latency）。

2
週二：後端核心 API 開發
完成搜尋與模糊比對功能
建立基本 CRUD API（新增/查詢單字）。

實作模糊搜尋演演算法（Fuzzy Match API），確保輸入拼錯字母時能回傳相關單字。

3
週三：前端 UI 與搜尋欄整合
打造直覺搜尋介面
製作搜尋首頁與單字詳細頁（Card 樣式）。

實現 Dropdown 下拉選單：處理動態搜尋與拼字建議顯示。

實作關鍵字/情境標籤（Tags）點擊篩選功能。

4
週四：測試、部署與收集回饋
上線提供給同學使用
將前端部署至 Vercel，後端部署至 Render。

發布給系上同學測試，針對拼字修正精準度與單字補充進行迭代。
